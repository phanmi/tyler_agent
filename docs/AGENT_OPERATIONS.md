# Agent service operation bridge

[Migration tracker](AGENT_MIGRATION.md) | [Protocol contract](AGENT_PROTOCOL.md) | [Session lifecycle](AGENT_SESSION.md)

Step 6 implements Java's allowlisted service access; Step 7 implements the Python model loop and six tool adapters. Step 8 verifies the complete HTTP/Python/database path with a fake provider and temporary storage. The bridge is always wired for the sole Python agent implementation. This page inventories the preserved adapter behavior, extension boundaries, and integration evidence.

## Dispatch and ownership

`PythonWorker` validates framing, session, direction, values, and request/operation state before invoking `IOperationDispatcher` on its callback executor. [ServiceOperationDispatcher](../src/main/java/org/tyler/service/agent/bridge/ServiceOperationDispatcher.java) additionally validates standalone input against the existing operation-request schema through `MessageValidator`, then looks up an `IOperationHandler` in an immutable map. The dispatcher has no feature-service dependencies or operation switch.

[OperationBridgeConfiguration](../src/main/java/org/tyler/config/OperationBridgeConfiguration.java) discovers handler components at startup and injects their collection. Each handler declares its case-sensitive protocol operation name; Spring bean names do not determine routing. `MessageValidator` derives the allowed names from the shared protocol schema. Registry construction rejects null handlers, blank names, unapproved names, duplicates, and missing operations before requests can execute.

| Private operation | Public tool name (case-sensitive) | Destination | Transport result |
|---|---|---|---|
| `food.insert_all` | `recordFood` | `IFoodService.insertFoods` | `{foods: [{id, food}, ...]}` in the input's order; each generated ID is a decimal string. The foods are saved in one transaction: all of them, or none. |
| `workout_plan.generate_save` | `generateWorkoutPlan` | `IWorkoutPlanService.generateAndSave` | `{plan}` with the existing plan/day/workout fields. |
| `user_info.read` | `GetUserInfo` | `IUserInfoService.get` | `{profile}` with the stored capitalized property names. |
| `file.read` | `readFile` | `IFileSandboxRead.read` | `{content}` without newline or Unicode rewriting. |
| `file.write` | `writeFile` | `IFileSandboxWrite.write` | `{path}` echoing the requested path after successful writing. |
| `time.current` | `getCurrentTime` | Injected `Clock`, wired with the server's default time zone | `{text}` formatted as `yyyy-MM-dd HH:mm:ss z`. |

Domain rules remain in the existing services and validators. Negative domain numbers, null required values represented in the wire schema, and malformed calendar dates reach shared validation. Missing transport properties, incorrect JSON types, unknown operations, unsupported decimal notation/range, and invalid Unicode fail before service invocation. Model-facing tool execution and model message construction belong in Python.

Decimals use `BigDecimal` and plain decimal strings in transport, preserving fractional precision and trailing zeros without passing through binary floating point. Negative zero is normalized by Java. Existing protocol magnitude limits and signed-long ID limits remain unchanged. SQLite's existing `NUMERIC` affinity can normalize trailing zeros on a later database read; this step changes neither storage types nor persisted data. The immediate food result uses the value returned by the service, including its decimal scale.

The six implementations live in [bridge/handler](../src/main/java/org/tyler/service/agent/bridge/handler): `FoodInsertAllHandler`, `WorkoutPlanSaveHandler`, `UserInfoReadHandler`, `FileReadHandler`, `FileWriteHandler`, and `CurrentTimeHandler`. Each constructor receives only its required service, sandbox capability, or clock, plus the shared [OperationPayloadMapper](../src/main/java/org/tyler/service/agent/bridge/OperationPayloadMapper.java) where conversion is needed. The mapper owns domain-object decoding and plain-decimal result encoding. Conversion failures retain their causes as internal failures; a serialization failure after a write is never classified as a domain rejection.

## Adding an operation

1. Define the private operation in the shared protocol contract, schema, and fixtures. Coordinate Java/Python compatibility and write-effect classification, including any required protocol-version change. Registering a Java bean alone does not authorize a new wire operation.
2. Add a focused class implementing `IOperationHandler` under `service/agent/bridge/handler`. Annotate it with `@Component`; return the schema's exact operation name from `operationName()`.
3. Inject the required service or sandbox interface through the constructor. Use `OperationPayloadMapper` for shared object conversion. Keep domain rules and transaction orchestration in the service, and preserve original exceptions for the supervisor's cause ledger. Handlers receive input after protocol validation.
4. Add handler tests for delegation, output, and failures. Extend shared protocol fixtures and verify production Spring registration, malformed-input rejection, and the architecture boundary. Add persistence integration coverage when the operation changes stored data.
5. Run the affected checks and update this inventory and the migration record. No dispatcher switch, central service field list, or central handler construction list needs editing.

## Tool parsing and output contracts

Each Python [builtin tool package](../agent-python/src/tyler_agent/tools/builtin) owns its adapter and `definition.json`; shared [argument parsing](../agent-python/src/tyler_agent/tools/parsing.py) enforces each tool's declared argument types and fields, and [result rendering](../agent-python/src/tyler_agent/tools/rendering.py) preserves the released output formats. The frozen [release schema fixture](../contracts/agent/v3/fixtures/tool-definitions.json) replaces comparisons against the retired Java builders. `PythonToolContractTest` verifies complete schemas and shared output goldens; Python registry/tool tests check the same contracts. Domain validation stays in Java.

### Adding a Python tool

1. Add a package under `agent-python/src/tyler_agent/tools/builtin/<tool_name>/`, containing `__init__.py`, `adapter.py`, and `definition.json`. Keep one tool's name, description, and full model schema in its own definition file.
2. Implement `async def execute(raw: str, context: ToolContext) -> str` in `adapter.py`. The [`ToolContext`](../agent-python/src/tyler_agent/tools/contracts.py) belongs to the current run: `context.operation` requests a Java operation, `context.respond` sends one request to the run's provider and model with a transcript and tools the tool chooses, `context.conversation` is the run's saved history plus the current user message as text, and `context.earlier_calls` is every tool call the run finished before this one, with its arguments and result, which the registry fills in for every tool. Parse `raw` with the helpers in [parsing.py](../agent-python/src/tyler_agent/tools/parsing.py) before calling `context.operation`, and raise `ArgumentsRejected` for arguments that do not match the definition, so they go back to the model. Any other exception while parsing, or an `ArgumentsRejected` after an operation was requested, fails the run as `worker/INTERNAL_FAILURE`. Keep handlers free of mutable request state; call Java for domain/storage work and keep result formatting at this boundary.
3. Add dedicated tests under `agent-python/tests/`. Frozen release fixtures protect existing tool schemas and output formats; new operations also require coordinated protocol/schema/fixture and Java-handler changes. Adding a Python tool cannot expand Java's operation allowlist.
4. Run Python checks and rebuild/smoke-test the worker. Discovery and PyInstaller collect the bundled packages automatically; no central handler map, import list, or combined JSON catalog needs editing.

Discovery reads only the trusted bundled namespace, never a model-supplied module path. Packages are sorted by folder name for deterministic definition order. Missing definitions/adapters, invalid schemas or handler signatures, duplicate names, and an empty catalog fail startup before readiness. The worker validates one catalog and reuses it across requests; each request binds its own tool context (Java operations, model and conversation) and keeps its own record of the tool calls it has finished, and providers receive defensive copies of definitions. The package `__init__.py` only exports the public facade. `test_tool_registry.py` covers extension, invalid registration, discovery, and isolation; relocated-bundle checks verify dynamic imports and all definition resources.

| Python adapter | Parsing behavior before the service operation | Model-visible result |
|---|---|---|
| [recordFood](../agent-python/src/tyler_agent/tools/builtin/food_record/adapter.py) | Requires a `foods` list holding every food of the message, with at least one food object; a missing, null or empty list is rejected. Enforces the advertised schema's types and fields for each food: text fields must be JSON strings and nutrition fields JSON numbers, so booleans, numbers as names/units, and quoted numbers are rejected, as are unknown properties at any level. Missing or null record components/fields still pass as null to the shared food validator. Every food's types are checked before any number is encoded. Valid numbers are encoded exactly as plain decimal strings; a number beyond the two-billion protocol bound fails the run as `INVALID_ARGUMENT`. The parsed foods then go through the [food checks](#food-verification) before anything is saved, and the foods the checks leave are saved together in one `food.insert_all`. | Pretty JSON with a `recorded` list of the saved foods, each in the compatible food format with numeric values, excluding the generated ID. A record the checks removed is listed under `notRecorded` with the name the model gave and the `reason`, beside a `note` to tell the user which records were left out and why, and not to record them again. |
| [generateWorkoutPlan](../agent-python/src/tyler_agent/tools/builtin/workout_plan/adapter.py) | Requires a JSON object with only start date/goal/equipment; any other property, including `preview`, is rejected. Each supplied non-null field must be a string. Missing/null fields and enum values pass to service validation. | Pretty plan JSON with numeric weights, nullable activities, and empty rest-day workout arrays. |
| [GetUserInfo](../agent-python/src/tyler_agent/tools/builtin/user_info/adapter.py) | Ignores arguments. The service owns profile loading, normalization, and existing missing/unreadable-file fallback. A null top-level stored profile fails; the bridge does not invent a profile. Nullable components are retained. | Java-record-style `UserInfo[user=User[...], other=Other[...]]`, with component order and null/string rendering specified in the protocol guide. |
| [readFile](../agent-python/src/tyler_agent/tools/builtin/file_read/adapter.py) | Requires an object whose only property is a string `path`; a missing, null, or non-string path or any other property is rejected. Blank, unsafe, and protected paths are sandbox rules: the bridge rejects them as `INVALID_ARGUMENT`. | Raw file contents. |
| [writeFile](../agent-python/src/tyler_agent/tools/builtin/file_write/adapter.py) | Requires an object with exactly a string `path` and string `content`; anything else is rejected, so object, array, number, boolean, or null content can never erase a file. An empty content string intentionally writes an empty file. Path rules are the sandbox's, as for `readFile`. | `Wrote ` followed by the requested path. |
| [getCurrentTime](../agent-python/src/tyler_agent/tools/builtin/time_current/adapter.py) | Ignores arguments. Python requests an empty-input operation instead of substituting its own local clock/time zone. | Server-local time text in the existing format. |

No-argument tools send `{}` to Java after their adapter parsing. Public tool names are not accepted as private operation names. Protocol version 3 (like the versions before it) excludes scientific notation and decimal magnitudes above two billion; adapters must honor that documented transport restriction rather than round or silently truncate values. Expanded ISO years remain strings through Python and are interpreted by Java. The seven-day upper-date bound belongs to the shared plan service.

### Amounts and units

When the user gives an amount, `recordFood`'s [definition](../agent-python/src/tyler_agent/tools/builtin/food_record/definition.json) tells the chat model to save that amount and the user's own word for its unit: cup, slice, oz, scoop, can, "medium", and so on, even when the unit is uncommon. The model does not convert the amount to grams or millilitres, and does not add a conversion to the unit, such as `cup (240 ml)`. When the user gives two units for one food, such as "one 2 oz bar", either is saved. Nutrition values are for that amount in that unit. When the user gives no amount, the model estimates one.

Java's food validation accepts any non-blank unit, and the Python adapter passes the unit through unchanged. Daily totals add up nutrition values, never amounts, so units need no conversion for them. The [name and count check](#food-verification) has a converted or annotated unit written again in the user's unit.

### Estimated nutrition values

`recordFood`'s [definition](../agent-python/src/tyler_agent/tools/builtin/food_record/definition.json) tells the chat model where nutrition values the user did not state come from:

- **A packaged or restaurant food:** the brand's published nutrition for that product and amount.
- **Any other food, or a brand whose values the model does not know:** USDA FoodData Central values for that food, or for the closest generic food in FoodData Central.

Nutrition values the user states are saved exactly as stated, whatever these sources say. The agent does not look values up: it relies on what the model knows of these sources. The [content check](#food-verification) judges values against the same sources, and its correction estimates from them too.

### Food verification

`recordFood` checks the foods of a call with the run's provider and model before it requests `food.insert_all` for them. The chat model is offered only `recordFood`. Each check and each correction is its own model request with a tool of its own, so the chat model cannot skip one. [`checks.py`](../agent-python/src/tyler_agent/tools/builtin/food_record/checks.py) runs the checks in the order below, each on the list the one before it leaves. The name and count check is switched off in every run, and the content check in every chat of the app, so a chat makes only the date check; see **The switches** below.

Before the checks, the tool reads what they judge the foods against, once for the call: today's date through `time.current`, the conversation (saved history plus the current message), and the tool calls the run finished earlier, each with its arguments and result. The conversation and the calls go into a prompt as JSON text. So a message or a tool result, such as the contents of a file, stays data and cannot change what a check is asked to do.

| Check | Tools | What the model is shown | What it changes |
|---|---|---|---|
| Name and count, [`name_check.py`](../agent-python/src/tyler_agent/tools/builtin/food_record/name_check.py) | `verifyFoodList` | The conversation, the earlier calls, and each food's number, name, amount and unit | Off in every run. When it is switched on: it removes a record that is not one food the message asks to record: an invented food, a record for a whole meal, a food listed twice, or one an earlier `recordFood` call of the run already saved. It adds a food the message asks to record that has no record. It has the amount, unit and nutrition values written again for a food whose amount or unit differs from what the user said, as [above](#amounts-and-units). |
| Date, [`date_check.py`](../agent-python/src/tyler_agent/tools/builtin/food_record/date_check.py) | `verifyFoodDates`, then `correctFoodDates` | Today's date, the conversation, the earlier calls, and each food's number, name and date | It corrects the date of a food that is not recorded on the day the user ate it. A food with no date is always corrected, whatever the check answers. A corrected date is a real day written as `YYYY-MM-DD`. Nothing else in the record changes. |
| Content, [`content_check.py`](../agent-python/src/tyler_agent/tools/builtin/food_record/content_check.py) | `verifyFoodNutrition` | The conversation, the earlier calls, and one food's name, amount, unit and nutrition values | Off in every chat of the app. When it is switched on: it has the nutrition values written again for a food with a value that differs from one the user stated. For a value the user did not state, it does so when the value is implausible for that food and amount, judged against the [sources above](#estimated-nutrition-values). A small difference from those sources is not a reason to reject. |

A check's answer points at a food by its number in the list it was shown.

**Corrections.** A missing food, a wrong amount and implausible nutrition values are each corrected by one `correctFood` request for each food ([`correction.py`](../agent-python/src/tyler_agent/tools/builtin/food_record/correction.py)). The request is shown the conversation, the earlier calls and today's date, and writes one whole record under `recordFood`'s own rules for units and nutrition values. The tool is given the part of `recordFood`'s description that says how one food is written, from "When the user gives an amount" on, and not the part about the `foods` list, which its arguments do not have. Python keeps only the fields that correction may change:

- for a missing food, the whole record;
- for a wrong amount or unit, the amount, the unit and the nutrition values, because the values belong to the amount;
- for implausible nutrition values, the nutrition values.

Corrections for different foods are sent at the same time, and so are the content checks, with at most 8 of a check's questions being asked at once (`MAX_QUESTIONS_TOGETHER`). The rest wait their turn. One call can carry any number of foods and the providers do not retry, so without the limit one rate-limit error on a long list would fail the run. A corrected value is saved without a second check.

**Values the user stated.** A value the user stated is right, however unusual it looks. The user can state it in the conversation, or in a tool result the message points to, such as a file. The content check is shown both for that reason. It rejects a record with a value that differs from a stated one, never rejects a value for matching what the user said, and judges plausibility only for the values the user did not state. Its correction keeps every stated value too, and its answer is not checked again.

**An answer that cannot be used.** A check's tool is offered but not forced, because Claude cannot force a tool call while adaptive thinking is on and DeepSeek's tool calls are not strict. So an answer can be a text reply, the wrong tool, several calls, or arguments that do not fit the tool. Two more kinds of answer cannot be used, because saving them would fail the chat:

- a `correctFood` record with a field missing or null, or with a negative number;
- a `correctFoodDates` date that is not a real day written as `YYYY-MM-DD`.

Java has both rules and applies them to every food it saves. Python repeats them only for these answers to its own tools, so that the question is asked again.

An answer that cannot be used is never read as "nothing is wrong":

- For the name and count check, the date check and their corrections, the question is asked again, four requests in all (`REQUIRED_ATTEMPTS`). Then the run fails as `provider/MODEL_ANSWER_UNUSABLE`, and nothing is saved. The user sees `The model could not complete a required check. Please try again` (HTTP 502). A request that itself fails is still `provider/PROVIDER_FAILURE`.
- For the content check and its correction, the question is asked once more (`OPTIONAL_ATTEMPTS`). Then the food goes on with the values it has.

**Saving.** No food is saved until every check has finished. A provider failure, a cancellation, or a required check that could not be answered ends the run with its usual code, and none of the call's foods is saved. The foods the checks leave are then saved in one `food.insert_all` request, which Java runs as one transaction: if Java rejects one food, or the database fails part of the way, none of the call's foods is saved. When the checks leave no food, no save is requested. A second `recordFood` call in the same run is a save of its own, so a failure in it does not undo the first. The tool result lists the saved foods under `recorded`. A record the checks removed is listed under `notRecorded` with its reason, beside a `note` that tells the chat model to tell the user which records were left out and why, and not to record them again. Only the name and count check removes a record.

**Cost.** A call with n foods costs one request for the date check, plus one when dates have to be corrected. When the content check is switched on, it costs n more, plus one for each food it has written again. The name and count check costs one more when it is switched on. Each request carries the conversation and the earlier calls, so the content check sends them once for each food. They all count against the run's existing deadline. Logs record only counts and attempts, never the conversation, a food or a reason.

**The switches.** The date check always runs. The other two checks are in the code and are switched off.

- **Name and count.** The name and count check runs when `RunSettings.check_names` is on, and the default is off. It costs a model request for every `recordFood` call, and the eval has not shown what it is worth: in the [full run on the low-cost models](evals/verification-overhaul/2026-11-18-verification-overhaul.md) it changed a record in 4 of 1,206 chats. [#118](https://github.com/phanmi/tyler_agent/issues/118) is to show whether it earns that cost, and the check stays off until it does. The run payload does not carry this switch.
- **Content.** The content check runs when `RunSettings.check_nutrition` is on. The run payload carries it as `checkNutrition`, and `PythonAgentService` sends `false` for every chat: the app has no setting that turns the check on. Even on the low-cost models, the nutrition values the chat model estimates are good enough without a second request. In the many-foods run of 2026-11-21 on the three low-cost models, the check left fully correct chats unchanged on one model, raised them by 4 of 60 on another and lowered them by 3 of 60 on the third, and each chat made more than twice the model requests. [#113](https://github.com/phanmi/tyler_agent/issues/113) records the run.

Code that drives the agent directly, such as tests and the eval harness, can set both switches. The eval harness runs every case with the content check off and on, which is how the check stays measured.

Limits of the checks:

- The model checks its own output. How often a check finds the right foods, dates and values is measured by the [eval harness](../agent-python/evals/README.md), not by the unit tests, which script the model's answers.
- A chat model that spreads a message's foods over several `recordFood` calls has each call checked and saved on its own. Only the name and count check, which is off, would remove a food that an earlier call already saved. With that check on, the first call's check can add a food that the second call carries, and the second call's check then has to remove it.
- With the name and count check off, nothing after the chat model removes a record that does not belong, adds a food the message left out, or corrects an amount or unit.
- With the content check off, nothing after the chat model changes a nutrition value.

## Persistence, failures, and file access

- Food saving appends every food of a `recordFood` call through `IFoodService.insertFoods`, in one transaction on the food database's own data source. Every food is validated before the first write, and a storage failure rolls back the ones already written, so a call's foods are saved whole or not at all. A transaction that cannot open or commit is a `SQL_WRITE` failure too. Equal entries retain independent generated IDs; the calendar's reads and deletions over HTTP use those IDs and the same service and DAO.
- Plan saving uses the existing transaction and data source. Sequential repeats reuse date/name matches, preserve existing IDs and manual edits, and do not imply concurrent deduplication. No new preview operation is exposed; the existing preview service remains read-only.
- The file bridge delegates to the [workspace file sandbox](FILE_SANDBOX.md). It rejects traversal and linked/special path components under the real configured root. The policy also covers SQLite paths and documents remaining races with concurrent filesystem writers, particularly Windows directory traversal and native SQLite opens. The bridge does not expand filesystem permissions or add path resolution of its own.
- Local service exceptions propagate unchanged into the supervisor's run ledger. Safe wire errors retain their established domain/SQL/file/internal classification; terminal Java wrappers retain local causes without returning them publicly. Unknown write outcomes remain conservative after failure. Tested transaction rollback does not justify assuming every thrown write exception means no effect.
- Serialization or transport failure after a write never triggers retry, delete compensation, or fallback. Operation success logs contain only the allowlisted name; no food/profile/file content is logged by the bridge.

Run `uv sync --locked --group dev` in `agent-python/` first, then `mvn -Dtest=AgentPersistenceIntegrationTest test` from the repository root. The normal `mvn test` / CI `mvn --batch-mode clean verify` selection includes this class automatically. Missing Python setup fails the test instead of skipping it. ## Python execution and operational limits

[run_agent](../agent-python/src/tyler_agent/agent.py) builds the initial request from Java's supplied history and current message, using the supplied model and all six tool definitions. Calls execute sequentially in response order. Each output uses its original `call_id`. Each continuation resends the whole run transcript (history, the current message, this run's model output and tool results) with `store=false`, so no provider keeps conversation state; OpenAI reasoning is requested as encrypted content and replayed unchanged. After five tool rounds, the last response's text/refusals are concatenated without separators; further calls are not executed. Empty output remains an empty successful reply. Java alone appends the successful exchange.

`open_provider` in [provider.py](../agent-python/src/tyler_agent/provider.py) picks the provider from the run's required `provider` field (`openai`, `anthropic`, or `deepseek`); Java fills it, with the model and that provider's key, from the user's saved settings. Every provider converts the shared transcript and tool types in [transcript.py](../agent-python/src/tyler_agent/transcript.py) to its own API and applies the same rules: a new asynchronous client for each run that closes after success, failure, or cancellation; the Java credential snapshot only; an explicit endpoint; zero SDK retries; a request timeout of the smaller of 60 seconds and the run deadline (Claude uses the run deadline, because its non-streaming thinking replies can take minutes); and SDK and HTTP loggers suppressed. No key is read or client created during readiness. Authentication/permission errors become `PROVIDER_AUTH`; other SDK and transport failures become `PROVIDER_FAILURE`, retaining local causes without logging or serializing provider detail. A tool call with an unknown tool name, or with arguments its adapter rejects as described below, goes back to the model as a fixed error result (counted against the round limit) instead of failing the chat; `ToolAdapters.execute` returns that result, and each adapter's parser decides which arguments to reject.

| Provider | Module and API | Provider-specific behavior |
|---|---|---|
| OpenAI | `ResponsesProvider` in `provider.py`; [Responses API](https://developers.openai.com/api/docs/guides/function-calling) at `https://api.openai.com/v1` | `store=false`; this run's reasoning, message, and function-call items replayed unchanged, with reasoning requested as encrypted content; strict function tools. A response whose `status` is not `completed` (for example `incomplete` at the output limit or after filtering) fails as `PROVIDER_FAILURE` before its text is used or any tool runs. |
| Claude | `ClaudeProvider` in `claude_provider.py`; Messages API at `https://api.anthropic.com` (`anthropic` SDK) | Adaptive thinking at the model's default effort and server-side fallback, both only for Claude 4.6 and later model IDs (`claude-<family>-<major>-<minor>`, optionally with a date); other custom IDs, such as `claude-sonnet-4-5-20250929`, get a plain request without either; `max_tokens` 16000; strict tools; all of a round's tool results in one user message; this run's content blocks, thinking and signatures included, replayed unchanged. The stop reason is checked before content: `refusal` (after Anthropic's server-side fallback model also declines) returns the fixed reply "Sorry, I can't help with that request." and runs no tools; `max_tokens` and other incomplete stops fail as `PROVIDER_FAILURE`. Thinking and tool-use blocks before the last `fallback` marker came from the declining model and are neither run nor replayed; text blocks are kept, as Anthropic specifies, though non-streaming responses already omit a declined partial. The `fallback` marker itself is replayed in its original position, because the API uses it to validate the thinking blocks around it. Telemetry is off. |
| DeepSeek | `DeepSeekProvider` in `deepseek_provider.py`; Chat Completions at `https://api.deepseek.com` (`openai` SDK) | Thinking disabled, because with tools DeepSeek requires the reasoning of every earlier turn and saved history has none; non-strict tools (strict mode needs DeepSeek's beta endpoint), so the worker's own argument parsing is the check, and this is the provider that can produce the malformed calls described below; assistant `tool_calls` followed by one `tool` message per result; only validated content and calls replayed. `stop` and `tool_calls` finish normally; `length`, `content_filter`, and server-side stops fail as `PROVIDER_FAILURE`. |

Saved history is plain text: earlier replies are sent as plain assistant messages (Claude skips empty ones, which it rejects). Only output from the current run carries provider-specific content for replay.

Each reply also carries the token usage its provider reported, as a `Usage` on the `AssistantTurn`: all input tokens, the part read from the provider's prompt cache, the part written to it, and output tokens. The three APIs count input differently (Claude reports cached input separately from `input_tokens`, while OpenAI and DeepSeek include it), so each provider module converts to the same terms. A reply with no token counts has no usage and is not a failure. The worker does not log usage or send it to Java; the [eval harness](../agent-python/evals/README.md) reads it to report cost.

The Python worker does not replay operations or fall back to Java. New operational bounds are 100 function calls and 1,000 output items per provider response, plus the existing 16 MiB text/frame bound and five-round limit. Oversized provider output fails before that response's tools execute. These are explicit resource limits for the Python implementation. The existing run and operation deadlines also apply.

An operation failure retains Java's validated category, code, and safe message. The terminal `failed` payload replaces the operation's `writeOutcome` with the aggregate for the whole run: a successful write followed by a failed read reports `committed`, even when that read reports `none`. Uncertainty still takes precedence. The original Java cause remains in the supervisor ledger; it is not serialized to Python.

Model arguments must be one complete JSON value; trailing non-whitespace after a value is rejected. This deliberately tightens Jackson's permissive trailing-token behavior for malformed arguments. Model numeric input is parsed exactly; valid scientific numeric arguments are converted to plain wire decimals within the existing two-billion protocol bound and a scale of 256 digits. A number beyond either limit still matches the schema, so it ends the run as `INVALID_ARGUMENT`. Zero is accepted whatever its exponent. Negative domain numbers, missing domain fields, and invalid calendar dates still reach Java validation.

Adapters reject wrong JSON types and undeclared properties before requesting any operation: the root must be an object, no key may repeat, every non-null field must have its declared type, and strings must be encodable as UTF-8. All types are checked before any number limit applies. File tools also require a string `path` and `content` and a non-blank `path`. Values are never coerced between types. Missing and null food and plan fields, and values outside an enum, are forbidden by the schemas but reach Java on purpose and end the run with its validation error. Arguments that fail the adapter checks, like malformed JSON or an unknown tool name, are not a run failure: the model receives the fixed tool result `{"error": "Tool call rejected: unknown tool name or arguments that do not match the tool's parameters. No action was taken."}`, which echoes nothing from the call, and may correct the call within the five-round limit. The worker logs a warning with the tool name only. Strict-schema providers (OpenAI, Claude) do not normally produce such calls; DeepSeek's non-strict tools can. Domain rejections and real storage failures from Java still end the run with their own category and HTTP mapping.

Earlier versions coerced these values instead, following the retired Java tools' `JsonNode.asText()` and default Jackson coercion. Object and array `content` became empty text and erased the target file, numbers and booleans became path, content, name, or unit text, quoted numbers became nutrition values, and unknown plan properties such as `preview` were ignored while the plan was saved. File argument errors were reported as `FILE_READ`/`FILE_WRITE` storage failures (HTTP 500). Issue #61 replaced that behavior with the rejection above.

The [eval harness](../agent-python/evals/README.md) in `agent-python/evals/` runs labelled food messages against a real provider with the nutrition check off and on, and reports accuracy, token usage, cost, and what each check changed and why. It is a development tool that makes paid calls, so it is run by hand; `test_evals_*.py` cover it with a fake model.

`test_agent.py` and `test_tools.py` cover orchestration and adapter parity. `test_provider.py`, `test_claude_provider.py`, and `test_deepseek_provider.py` send real SDK requests to an in-memory HTTP transport for each provider, covering request shape, multi-round tool use and replay, stop reasons, malformed output, error classification, disabled retries, client cleanup, and log redaction; no test calls a live provider. `test_runtime.py` controls cancellation, callback ordering, timeouts, and terminal messages. `test_worker_execution.py` exercises the real entry point and pipes with an injected fake provider. Production has no fake-provider environment switch or configurable test endpoint.
