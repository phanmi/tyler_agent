# Agent service operation bridge

[Migration tracker](AGENT_MIGRATION.md) | [Protocol contract](AGENT_PROTOCOL.md) | [Session lifecycle](AGENT_SESSION.md)

Step 6 implements Java's allowlisted service access; Step 7 implements the Python model loop and six tool adapters. Step 8 verifies the complete HTTP/Python/database path with a fake provider and temporary storage. The bridge is always wired for the sole Python agent implementation. This page inventories the preserved adapter behavior, extension boundaries, and integration evidence.

## Dispatch and ownership

`PythonWorker` validates framing, session, direction, values, and request/operation state before invoking `IOperationDispatcher` on its callback executor. [ServiceOperationDispatcher](../src/main/java/org/tyler/service/agent/bridge/ServiceOperationDispatcher.java) additionally validates standalone input against the existing operation-request schema through `MessageValidator`, then looks up an `IOperationHandler` in an immutable map. The dispatcher has no feature-service dependencies or operation switch.

[OperationBridgeConfiguration](../src/main/java/org/tyler/config/OperationBridgeConfiguration.java) discovers handler components at startup and injects their collection. Each handler declares its case-sensitive protocol operation name; Spring bean names do not determine routing. `MessageValidator` derives the allowed names from the shared protocol schema. Registry construction rejects null handlers, blank names, unapproved names, duplicates, and missing operations before requests can execute.

| Private operation | Public tool name (case-sensitive) | Destination | Transport result |
|---|---|---|---|
| `food.insert` | `recordFood` | `IFoodService.insertFood` | `{id, food}`; generated ID is a decimal string. |
| `workout_plan.generate_save` | `generateWorkoutPlan` | `IWorkoutPlanService.generateAndSave` | `{plan}` with the existing plan/day/workout fields. |
| `user_info.read` | `GetUserInfo` | `IUserInfoService.get` | `{profile}` with the stored capitalized property names. |
| `file.read` | `readFile` | `IFileSandboxRead.read` | `{content}` without newline or Unicode rewriting. |
| `file.write` | `writeFile` | `IFileSandboxWrite.write` | `{path}` echoing the requested path after successful writing. |
| `time.current` | `getCurrentTime` | Injected `Clock`, wired with the server's default time zone | `{text}` formatted as `yyyy-MM-dd HH:mm:ss z`. |

Domain rules remain in the existing services and validators. Negative domain numbers, null required values represented in the wire schema, and malformed calendar dates reach shared validation. Missing transport properties, incorrect JSON types, unknown operations, unsupported decimal notation/range, and invalid Unicode fail before service invocation. Model-facing tool execution and model message construction belong in Python.

Decimals use `BigDecimal` and plain decimal strings in transport, preserving fractional precision and trailing zeros without passing through binary floating point. Negative zero is normalized by Java. Existing protocol magnitude limits and signed-long ID limits remain unchanged. SQLite's existing `NUMERIC` affinity can normalize trailing zeros on a later database read; this step changes neither storage types nor persisted data. The immediate food result uses the value returned by the service, including its decimal scale.

The six implementations live in [bridge/handler](../src/main/java/org/tyler/service/agent/bridge/handler): `FoodInsertHandler`, `WorkoutPlanSaveHandler`, `UserInfoReadHandler`, `FileReadHandler`, `FileWriteHandler`, and `CurrentTimeHandler`. Each constructor receives only its required service, sandbox capability, or clock, plus the shared [OperationPayloadMapper](../src/main/java/org/tyler/service/agent/bridge/OperationPayloadMapper.java) where conversion is needed. The mapper owns domain-object decoding and plain-decimal result encoding. Conversion failures retain their causes as internal failures; a serialization failure after a write is never classified as a domain rejection.

## Adding an operation

1. Define the private operation in the shared protocol contract, schema, and fixtures. Coordinate Java/Python compatibility and write-effect classification, including any required protocol-version change. Registering a Java bean alone does not authorize a new wire operation.
2. Add a focused class implementing `IOperationHandler` under `service/agent/bridge/handler`. Annotate it with `@Component`; return the schema's exact operation name from `operationName()`.
3. Inject the required service or sandbox interface through the constructor. Use `OperationPayloadMapper` for shared object conversion. Keep domain rules and transaction orchestration in the service, and preserve original exceptions for the supervisor's cause ledger. Handlers receive input after protocol validation.
4. Add handler tests for delegation, output, and failures. Extend shared protocol fixtures and verify production Spring registration, malformed-input rejection, and the architecture boundary. Add persistence integration coverage when the operation changes stored data.
5. Run the affected checks and update this inventory and the migration record. No dispatcher switch, central service field list, or central handler construction list needs editing.

## Tool parsing and output contracts

Each Python [builtin tool package](../agent-python/src/tyler_agent/tools/builtin) owns its adapter and `definition.json`; shared [argument parsing](../agent-python/src/tyler_agent/tools/parsing.py) and [result rendering](../agent-python/src/tyler_agent/tools/rendering.py) preserve the released compatibility rules. The frozen [release schema fixture](../contracts/agent/v2/fixtures/tool-definitions.json) replaces comparisons against the retired Java builders. `PythonToolContractTest` verifies complete schemas and shared output goldens; Python registry/tool tests check the same contracts. Domain validation stays in Java.

### Adding a Python tool

1. Add a package under `agent-python/src/tyler_agent/tools/builtin/<tool_name>/`, containing `__init__.py`, `adapter.py`, and `definition.json`. Keep one tool's name, description, and full model schema in its own definition file.
2. Implement `async def execute(raw: str, operation: Operation) -> str` in `adapter.py`. The injected `operation` is scoped to the current run. Keep handlers free of mutable request state; call Java for domain/storage work and preserve adapter parsing/formatting at this boundary.
3. Add dedicated tests under `agent-python/tests/`. Frozen release fixtures protect existing tool schemas and output formats; new operations also require coordinated protocol/schema/fixture and Java-handler changes. Adding a Python tool cannot expand Java's operation allowlist.
4. Run Python checks and rebuild/smoke-test the worker. Discovery and PyInstaller collect the bundled packages automatically; no central handler map, import list, or combined JSON catalog needs editing.

Discovery reads only the trusted bundled namespace, never a model-supplied module path. Packages are sorted by folder name for deterministic definition order. Missing definitions/adapters, invalid schemas or handler signatures, duplicate names, and an empty catalog fail startup before readiness. The worker validates one catalog and reuses it across requests; each request binds its own Java operation capability, and providers receive defensive copies of definitions. The package `__init__.py` only exports the public facade. `test_tool_registry.py` covers extension, invalid registration, discovery, and isolation; relocated-bundle checks verify dynamic imports and all definition resources.

No-argument tools send `{}` to Java after their adapter parsing. Public tool names are not accepted as private operation names. Protocol version 2 (like version 1) excludes scientific notation and decimal magnitudes above two billion; adapters must honor that documented transport restriction rather than round or silently truncate values. Expanded ISO years remain strings through Python and are interpreted by Java. The seven-day upper-date bound belongs to the shared plan service.

## Persistence, failures, and file access

- Food insertion appends through the same service/DAO path used by HTTP. Equal entries retain independent generated IDs; subsequent calendar reads/deletions use those IDs.
- Plan saving uses the existing transaction and data source. Sequential repeats reuse date/name matches, preserve existing IDs and manual edits, and do not imply concurrent deduplication. No new preview operation is exposed; the existing preview service remains read-only.
- The file bridge delegates to the [workspace file sandbox](FILE_SANDBOX.md). It rejects traversal and linked/special path components under the real configured root. The policy also covers SQLite paths and documents remaining races with concurrent filesystem writers, particularly Windows directory traversal and native SQLite opens. The bridge does not expand filesystem permissions or add path resolution of its own.
- Local service exceptions propagate unchanged into the supervisor's run ledger. Safe wire errors retain their established domain/SQL/file/internal classification; terminal Java wrappers retain local causes without returning them publicly. Unknown write outcomes remain conservative after failure. Tested transaction rollback does not justify assuming every thrown write exception means no effect.
- Serialization or transport failure after a write never triggers retry, delete compensation, or fallback. Operation success logs contain only the allowlisted name; no food/profile/file content is logged by the bridge.

## Verification boundary

`ServiceOperationDispatcherTest` verifies all six shared result fixtures, exact decimal/ID conversion, malformed-input rejection before dependency access, and exception identity. `BridgeValidationTest` runs real food/plan services and compares shared validation errors with direct service calls, including missing fields, dates, negative numbers, expanded years, and the last representable week.

`OperationRegistryTest` verifies registration failures, immutable registration, and validation before handler execution. `OperationBridgeConfigurationTest` verifies actual Spring discovery, Python-only wiring, and startup rejection of invalid or incomplete registrations. Each handler has a dedicated unit test; `OperationPayloadMapperTest` covers decimal/null conversion and safe exceptions with retained causes.

`BridgePersistenceTest` uses the production Spring handler configuration, temporary SQLite databases, and the real sandbox/services. It covers a child-JVM worker callback inserting food, independent IDs and deletion, plan rollback after partial inserts, repeated saves preserving edits, and file restrictions. `ServiceBoundaryTest` checks compiled bridge dependencies for DAO/DAL, JDBC, and provider SDK references, and prevents the dispatcher from depending on feature services, models, or sandbox implementations. `PythonAgentConfigurationTest` proves exactly one real dispatcher is wired to the shared dependency instances.

`AgentPersistenceIntegrationTest` establishes the Step 8 HTTP → Java → real Python subprocess → Java service boundary using a real loopback server and temporary SQLite/history files. Only the model is replaced by the test-only `persistence_worker.py` provider; the production worker entry point, runtime, adapters, protocol, handler registry, services, and DAOs execute normally. The suite covers food append/identity/calendar deletion, read-only preview, repeat plan saves preserving edits/IDs, actual rollback after partial inserts, HTTP failure classification, history completion, concurrent requests, deadline cancellation, late results, worker death, and shutdown. A test dispatcher barrier delays a real service result after completion; a SQLite trigger injects a real insert failure. Neither replaces persistence with mocked success or delete-based cleanup.

Run `uv sync --locked --group dev` in `agent-python/` first, then `mvn -Dtest=AgentPersistenceIntegrationTest test` from the repository root. The normal `mvn test` / CI `mvn --batch-mode clean verify` selection includes this class automatically. Missing Python setup fails the test instead of skipping it. No live provider or user workspace is used. This is development-interpreter integration evidence; clean-machine desktop packaging and live-provider rollout remain later gates.

## Python execution and operational limits

[run_agent](../agent-python/src/tyler_agent/agent.py) builds the initial request from Java's supplied history and current message, using the supplied model and all six tool definitions. Calls execute sequentially in response order. Each output uses its original `call_id`. Each continuation resends the whole run transcript (history, the current message, this run's model output and tool results) with `store=false`, so no provider keeps conversation state; OpenAI reasoning is requested as encrypted content and replayed unchanged. After five tool rounds, the last response's text/refusals are concatenated without separators; further calls are not executed. Empty output remains an empty successful reply. Java alone appends the successful exchange.

`open_provider` in [provider.py](../agent-python/src/tyler_agent/provider.py) picks the provider from the run's required `provider` field (`openai`, `anthropic`, or `deepseek`); Java fills it, with the model and that provider's key, from the user's saved settings. Every provider converts the shared transcript and tool types in [transcript.py](../agent-python/src/tyler_agent/transcript.py) to its own API and applies the same rules: a new asynchronous client for each run that closes after success, failure, or cancellation; the Java credential snapshot only; an explicit endpoint; zero SDK retries; a request timeout of the smaller of 60 seconds and the run deadline; and SDK and HTTP loggers suppressed. No key is read or client created during readiness. Authentication/permission errors become `PROVIDER_AUTH`; other SDK and transport failures become `PROVIDER_FAILURE`, retaining local causes without logging or serializing provider detail.

| Provider | Module and API | Provider-specific behavior |
|---|---|---|
| OpenAI | `ResponsesProvider` in `provider.py`; [Responses API](https://developers.openai.com/api/docs/guides/function-calling) at `https://api.openai.com/v1` | `store=false`; this run's reasoning, message, and function-call items replayed unchanged, with reasoning requested as encrypted content; strict function tools. A response whose `status` is not `completed` (for example `incomplete` at the output limit or after filtering) fails as `PROVIDER_FAILURE` before its text is used or any tool runs. |
| Claude | `ClaudeProvider` in `claude_provider.py`; Messages API at `https://api.anthropic.com` (`anthropic` SDK) | Adaptive thinking at the model's default effort; `max_tokens` 16000; strict tools; all of a round's tool results in one user message; this run's content blocks, thinking and signatures included, replayed unchanged. The stop reason is checked before content: `refusal` (after Anthropic's server-side fallback model also declines) returns the fixed reply "Sorry, I can't help with that request." and runs no tools; `max_tokens` and other incomplete stops fail as `PROVIDER_FAILURE`. Blocks from a model that handed over to a fallback are neither run nor replayed. Telemetry is off. |
| DeepSeek | `DeepSeekProvider` in `deepseek_provider.py`; Chat Completions at `https://api.deepseek.com` (`openai` SDK) | Thinking disabled, because with tools DeepSeek requires the reasoning of every earlier turn and saved history has none; non-strict tools (strict mode needs DeepSeek's beta endpoint), so the worker's own argument parsing is the check; assistant `tool_calls` followed by one `tool` message per result; only validated content and calls replayed. `stop` and `tool_calls` finish normally; `length`, `content_filter`, and server-side stops fail as `PROVIDER_FAILURE`. |

Saved history is plain text: earlier replies are sent as plain assistant messages (Claude skips empty ones, which it rejects). Only output from the current run carries provider-specific content for replay.

The Python worker does not replay operations or fall back to Java. New operational bounds are 100 function calls and 1,000 output items per provider response, plus the existing 16 MiB text/frame bound and five-round limit. Oversized provider output fails before that response's tools execute. These are explicit resource limits for the Python implementation. The existing run and operation deadlines also apply.

An operation failure retains Java's validated category, code, and safe message. The terminal `failed` payload replaces the operation's `writeOutcome` with the aggregate for the whole run: a successful write followed by a failed read reports `committed`, even when that read reports `none`. Uncertainty still takes precedence. The original Java cause remains in the supervisor ledger; it is not serialized to Python.

Model arguments must be one complete JSON value; trailing non-whitespace after a value is rejected. This deliberately tightens Jackson's permissive trailing-token behavior for malformed arguments. Model numeric input is parsed exactly; valid scientific numeric arguments are converted to plain wire decimals within the existing two-billion protocol bound. Negative domain numbers, missing domain fields, and invalid calendar dates still reach Java validation. Numeric file path/content coercion uses decimal text without binary-floating-point rounding; ordinary text, booleans, empty content, and container-to-empty-text behavior remain compatible. These edge-case decisions do not change the advertised string-based file schemas or application domain rules.

`test_agent.py` and `test_tools.py` cover orchestration and adapter parity. `test_provider.py`, `test_claude_provider.py`, and `test_deepseek_provider.py` send real SDK requests to an in-memory HTTP transport for each provider, covering request shape, multi-round tool use and replay, stop reasons, malformed output, error classification, disabled retries, client cleanup, and log redaction; no test calls a live provider. `test_runtime.py` controls cancellation, callback ordering, timeouts, and terminal messages. `test_worker_execution.py` exercises the real entry point and pipes with an injected fake provider. Production has no fake-provider environment switch or configurable test endpoint.
